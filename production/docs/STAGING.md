# Staging — what it is and how to use it

*Built 3–4 Oct 2026 (board card R-106). Replaces the 27 Sep plan, which pointed staging at the
old hosted Supabase project; that plan was never built. Staging is now a small, separate copy of
the production stack inside the same Google Cloud project, `resellsubsos-prod`.*

## In one line

**local (your laptop) → staging (test copy, same as live) → live (customers)**. Every change
that touches the database or money goes through staging first.

## The pieces

| Piece | Production | Staging |
|---|---|---|
| App | Cloud Run `resellersos` (asia-southeast1), 1 warm instance | Cloud Run `resellersos-staging`, scales to 0 when unused |
| App URL | https://reselleros.anutech.in | https://resellersos-staging-njvk4nxhdq-as.a.run.app |
| Database | Cloud SQL `resellersos-db` | Cloud SQL `resellersos-staging-db` (db-f1-micro), a **clone of live with every row wiped** |
| Data plane (auth / REST / storage) | VM `supabase-gateway`, https://api.anutech.in | VM `staging-gateway` (35.240.252.6), https://35-240-252-6.sslip.io |
| Deploy trigger | push to branch `deploy` | push to branch `staging` (trigger `resellersos-staging-on-push`) |
| Secrets | service env | Secret Manager: `staging-service-role-key`, `staging-cron-secret`, `staging-secrets-master-key` |
| Crons | Cloud Scheduler | **none**, on purpose |
| Email / WhatsApp / payments / domains | live keys | **none**: no Resend, no ResellerClub/DirectAdmin, no Google login; Razorpay test key only, if ever added |

`sslip.io` maps the name `35-240-252-6.sslip.io` to the IP by itself, so staging needs no DNS
record. To use `staging-api.anutech.in` instead later: add an A record → 35.240.252.6, change the
host in `supabase/cloudsql/staging/Caddyfile` and `API_URL` in the setup script, rerun it, and
change `_SUPABASE_URL` on the trigger.

## The deploy flow

1. Work is committed on `manager-pardeep` (tests green locally).
2. **Migrations first on staging:** upload to `gs://resellsubsos-prod-rehearsal/golive/`, then
   `gcloud sql import sql resellersos-staging-db gs://…/<file>.sql --database=resellersos --user=resellersos_migration --project=resellsubsos-prod`.
   Run the matching `supabase/tests/*.test.sql` the same way (`--user=postgres`): an import
   that finishes without ERROR means every assertion passed.
3. **Staging train** (manager, every 2–3 hours — see `docs/STAGING-TRAIN.md`):
   `node scripts/ops/staging-train.mjs` (dry run), then
   `node scripts/ops/staging-train.mjs --db-done --push`. It merges the newest CI-green commit
   of `manager-pardeep` into `staging` (`--no-ff`, never a force push — staging carries R-161
   commits that `manager-pardeep` lacks) → Cloud Build builds the staging image
   (its own `_IMAGE` path, so production's `:latest` is never touched) and deploys
   `resellersos-staging`.
4. Check on the staging URL (AI tester / by hand). Nothing there is real: break anything.
5. Only then, after 17:00 IST and with Pardeep's yes: backup → the same migrations on
   `resellersos-db` → `git push anutech manager-pardeep:deploy`.

## Safety rules

- The staging DB carries `public.zz_staging_marker`; every staging script refuses to run
  where that table is missing. The live DB never has it.
- Never copy live data into staging again. If staging needs a fresh schema, clone live and
  run the wipe scripts immediately (R-106 log, 3 Oct 2026), or apply migrations to it.
- Staging secrets were generated by `supabase/cloudsql/staging/setup-staging-secrets.sh`;
  nothing secret was printed. Rerunning it rotates every staging password and key.
- Test accounts on staging are made by signing up on the staging URL (email auto-confirmed).
