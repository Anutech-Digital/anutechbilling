# ResellerOS ↔ DSP — Billing Integration API (Phase 1: Read)

This is the **billing-app side** of the DSP integration spec. It lets the DSP
support platform read a customer's live billing status (plan, payments,
subscriptions) so it can gate support access.

**Status:** Phase 1 (read APIs + API-key auth) — **LIVE**.
Phase 2 (outbound webhooks for instant lock/unlock) — planned, not yet built.

---

## 1. Base URL + auth

| | |
|---|---|
| **Production base** | `https://resellersos-njvk4nxhdq-el.a.run.app/api/v1` |
| **Auth** | `Authorization: Bearer <API_KEY>`  (or `X-API-Key: <API_KEY>`) |
| **Format** | REST / JSON / UTF-8 |
| **Errors** | HTTP status + `{ "error": "message", "code": "..." }` |

The API key is generated by the reseller owner in **ResellerOS → Settings →
Integrations → Support platform API (DSP)**. It is shown once; store it
server-side only. Each key is scoped to ONE reseller (tenant) — it can only
read that reseller's customers.

Missing/invalid/revoked key → `401 { "error": "Invalid or missing API key", "code": "unauthorized" }`.

There is currently **no hard rate limit**; please be reasonable (cache
short-term on your side). A limit will be added later if needed.

---

## 2. Customer identity key

`billing_customer_id` = the customer's **customer number** (e.g. `C-00001`),
stable and unique per reseller. The raw UUID is also accepted on the path as a
fallback. Store the `billing_customer_id` returned by the API against your DSP
customer and use it for all lookups.

---

## 3. Endpoints (all GET, all tenant-scoped)

### 3.0 List all customers (for "Sync all")
`GET /customers?page=1&per_page=100`  (per_page max 200)

```json
{
  "customers": [
    { "id": "C-00001", "billing_customer_id": "C-00001", "name": "test1",
      "email": "test1@gmail.com", "domain": null, "status": "active" }
  ],
  "page": 1, "per_page": 100, "total": 2, "pages": 1
}
```

`id` == `billing_customer_id` (same value; `id` is provided because your list
consumer keys on it). Subscriptions/invoices are NOT embedded — fetch per
customer via 3.2–3.5. Iterate `page` from 1..`pages` to sync everyone.

### 3.1 Customer lookup
`GET /customers/{billing_customer_id}`
`GET /customers?email=user@acme.com`  (secondary fallback for initial link)

```json
{
  "billing_customer_id": "C-00001",
  "name": "test1",
  "email": "test1@gmail.com",
  "domain": null,
  "status": "active"          // active if any active subscription, else inactive
}
```

### 3.2 Subscriptions
`GET /customers/{billing_customer_id}/subscriptions`

```json
[
  {
    "id": "06ea43fa-75c4-417c-a99e-2e46f331524f",
    "product": "Google Workspace Business Starter",
    "plan": "annual",                    // annual | monthly (derived from date span)
    "seats": 10,
    "status": "active",                  // active | suspended | expired | cancelled
    "start_date": "2026-07-14",
    "renewal_date": "2027-07-14",
    "amount": 132000,                    // annualised, integer INR (rupees)
    "currency": "INR",
    "domain": "acme.in",                 // the domain the plan is for, or null (R-1770)
    "vendor": "google"                   // google | microsoft | hosting | … (R-1770)
  }
]
```

### 3.3 Invoices
`GET /customers/{billing_customer_id}/invoices`

```json
[
  {
    "id": "INV-ET-2026-27-0002",
    "number": "INV-ET-2026-27-0002",
    "amount": 155760,
    "currency": "INR",
    "status": "paid",                    // paid | unpaid | overdue | cancelled
    "issue_date": "2026-07-14",
    "due_date": "2026-08-13",
    "pdf_url": "https://.../api/v1/documents/invoice/INV-ET-2026-27-0002/pdf?token=…"
  }
]
```

`pdf_url` is a ready-to-open link (GST Tax Invoice PDF, rendered on demand). It
carries a signed token, so a browser can open/download it directly — no Bearer
header needed. Treat the URL as a secret (anyone with the link can view that one
document). Returns `application/pdf`; bad/missing token → 403, unknown id → 404.

### 3.4 Quotes / pending payments
`GET /customers/{billing_customer_id}/quotes`

```json
[
  {
    "id": "Q-ET-2026-27-0015",
    "amount": 155760,
    "currency": "INR",
    "status": "accepted",                // pending | accepted | expired
    "pdf_url": "https://.../api/v1/documents/quote/Q-ET-2026-27-0015/pdf?token=…",
    "payment_url": "https://.../quote/Q-ET-2026-27-0015/accept",
    "valid_until": "2026-08-13",         // the quote's expiry date, or null (R-1770)
    "title": "Google Workspace Business Starter"  // the quote's plan name, or null (R-1770)
  }
]
```

### 3.5 Payments / transactions
`GET /customers/{billing_customer_id}/payments`

```json
[
  {
    "id": "466ff552-347d-4257-b62f-18b8045e0559",
    "amount": 155760,
    "currency": "INR",
    "reference": "razorpay_pay_xxx",
    "method": "upi",
    "paid_at": "2026-07-14T07:13:21.496483+00:00",
    "invoice_id": "INV-ET-2026-27-0002"   // derived via the payment's quote
  }
]
```

### 3.6 Support revenue from GST invoices (R-2079)
`GET /support/invoices/summary?from=YYYY-MM-DD&to=YYYY-MM-DD` — scope `read`.

DSP's support revenue, taken from Billing's GST tax invoices (not from DSP payments).
Counts only **issued Tax Invoices** (status pending / paid / overdue — no draft, no void,
no Bill of Supply, no imported Zoho opening invoice) that carry a support line (`SUP-…`), and
only the support lines' share of a mixed invoice. Credit notes raised against them in the
period are subtracted (in the month of the credit note). `from` / `to` are IST calendar dates,
both included, both required (400 otherwise).

```json
{
  "currency": "INR",
  "from": "2026-10-01",
  "to": "2026-10-31",
  "total_taxable": 1500.49,
  "total_gst": 270.09,
  "total_with_gst": 1770.58,
  "count": 2,                      // support invoices (credit notes do not change it)
  "by_plan": [
    { "plan_key": "enterprise", "taxable": 500.5, "gst": 90.09, "total": 590.59, "count": 1 },
    { "plan_key": "standard",   "taxable": 999.99, "gst": 180,  "total": 1179.99, "count": 1 }
  ],                                // plan_key: standard | enterprise | addon (product-wise add-on)
  "by_month": [
    { "month": "2026-10", "taxable": 1500.49, "total": 1770.58, "count": 2 }
  ]
}
```

Amounts here are rupees **exact to the paisa** (they may have two decimals) — summed in paise
and converted once, so `by_plan` and `by_month` always add up to the totals.

---

## 4. Money units

All amounts are **integer INR (rupees), not paise**. `amount: 132000` = ₹1,32,000.

## 5. Security notes

- HTTPS only. Store the key server-side; never expose it to a browser.
- Keys are tenant-scoped and revocable from Settings. A revoked key stops
  working immediately.
- A key gives **read** access to that reseller's customers, subscriptions,
  invoices, quotes and payments — treat it as a secret.

## 6. Phase 2 (planned) — outbound webhooks

To let DSP lock/unlock support instantly on billing changes, ResellerOS will
POST HMAC-signed events (`payment.received`, `invoice.paid`,
`subscription.*`) to a DSP endpoint. Not built yet — Phase 1 (polling these
read APIs) works today.

**Built (R-2067, 29 Oct 2026): support-plan sync.** When a support
subscription (vendor `support`) is created, or its plan / status / renewal date
changes, or its customer is archived/restored, a row is queued in
`support_sync_outbox` (triggers `trg_queue_support_sync`,
`trg_queue_support_sync_on_customer_status`). The cron
`/api/cron/support-sync` (every 5 min, switch "Support plan sync" on
/automation) POSTs each row's payload unchanged to
`${DSP_SUPPORT_URL}/api/sync/customer` with header
`X-Webhook-Secret: ${DSP_WEBHOOK_SECRET}`:

```json
{ "event_type": "subscription.updated",
  "data": { "billing_customer_id": "…", "name": "…", "email": "…", "domain": "…",
            "plan": "<subscription plan name, or 'free' when cancelled>",
            "plan_status": "active|cancelled|…", "plan_expiry": "YYYY-MM-DD" } }
```

2xx → row `sent`. Anything else → retried with back-off (10, 20, 40, 80 min);
the 5th failure → `failed`, counted on the cron's `[cron/support-sync]` stderr
line (health digest). One customer's rows go strictly oldest first. The secret
is a shared header for now; HMAC signing is still planned.
