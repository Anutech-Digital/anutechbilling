# Worker steps (ResellerOS) — follow exactly for EACH card

**FAST GATE (25 Oct 2026, Pardeep: "jo tumhe thik lage par kaam fast ho") — this replaces the "FULL suite" part of step 4.** Run:
- the card's own tests;
- `npx vitest related <changed files> --run`;
- the touched area's test folders;
- the repo-wide guard/scan tests: every *ratchet*, *scan*, *wiring* and *guard* test file;
- `npm run test:sql:local` ONLY if you added or changed SQL;
- `worker-lock tsc`, eslint on the changed files, and `worker-lock check`.

Do NOT run the full `npm run test` locally (about 40 minutes, and it crashes under load). GitHub CI runs it on every push, and `worker-lock push` still runs its guard files. After the push you wait for CI yourself (step 5b); if CI turns red, fixing that comes first.

**Fast type-check (R-1960, 26 Oct 2026).** `worker-lock tsc` and the tsc inside `worker-lock push` are incremental by default: after `next typegen`, a worktree with no `production/tsconfig.tsbuildinfo` of its own gets the shared one from `~/.claude/worker-tsc-cache/` (`WORKER_TSC_CACHE_DIR` overrides) whose key matches its TypeScript version, tsconfig.json AND generated route types (`.next/types` are global declarations — with a different route set tsc re-checks everything anyway, so such a cache is not used); after a GREEN tsc its build info becomes the shared one for that key (8 newest kept). It is the same `tsc --noEmit -p .` on the same files — tsc hashes every file and re-checks each changed file AND every importer whose types change (also two hops away), so a stale cache only makes it slower, never more lenient (tests/ops/worker-tsc-cache.test.ts proves it with real tsc; on the real repo a probe gave the identical 8 errors incremental and with `--full-tsc`). Measured on Pardeep's laptop, 26 Oct: fresh worktree before R-1960 525 s; a fresh worktree on the latest base with a card-sized change, from the shared cache, 141 s (and 148 s for one with a deliberate error, caught); the same worktree's next run 33–78 s. The first worker after a commit that adds/removes a route (~7% of commits) runs cold once and fills the cache. Skipping `next typegen` is not worth it (3 s). The old cold check stays available: `worker-lock tsc <CARD> --full-tsc` (or `push … --full-tsc`) runs `tsc --noEmit -p . --incremental false` with no cache read or written — use it if a tsc result ever looks wrong. CI still runs the full `npm run typecheck` on every push, and the red-CI push gate (R-1936) stops the next push on red.

**How many workers at once (R-1960).** At most **2 workers by day** (09:00–21:59 IST, while Pardeep works on the laptop) and **3 by night**; `worker-lock claim` refuses the next one with exit 3 (`WORKER_MAX` overrides). Four parallel tsc runs took the laptop to ~90 node processes.

**Waiting on CI does not use a slot (R-1973, 26 Oct 2026).** Only a card that is being BUILT counts toward the cap. A successful `worker-lock push` moves the card's lock to `ci-wait`: it no longer counts (another card may be claimed while `worker-lock ci` waits — CI takes ~29 min, `ci` waits up to 35 by default, R-1987), but it KEEPS all its claimed files — any claim or `check` that touches them is still refused with exit 2. `worker-lock ci` then: green → removes the lock (files free); red → `ci-red` (files still held, no slot); no answer in time → stays `ci-wait`. On red, take the slot back before fixing: `node scripts/ops/worker-lock.mjs claim <CARD> --fixes-red --card <cardfile>` (no paths; allowed even when the cap is full — red comes first; refused for a card that has no `ci-wait`/`ci-red` lock), fix, then `push <CARD> … --fixes-red`. A new push always puts the card back in a slot while it runs. `worker-lock list` shows each lock's state. Measured 26 Oct: R-1920 was refused with exit 3 while R-1961 was only waiting on CI.

**Run worker-lock from a worktree on the latest manager-pardeep.** Always run `node scripts/ops/worker-lock.mjs …` from a worktree made from a fresh `anutech/manager-pardeep` (or, for `resume`, from such a worktree's production/ folder) — never from the main clone while it sits on another branch (on Pardeep's laptop it is on `preview-0210`, whose worker-lock has no `resume`, no `ci`, no R-1958 guards and no tsc cache). The lock folder is shared, so any up-to-date worktree works.

**Stop the line on red CI (R-1936, 25 Oct 2026).** `worker-lock push` refuses (exit 7, "CI laal hai (<workflow> on <sha>: <failing tests>) — pehle woh theek karo") while the newest finished "CI" or "SQL tests" run on manager-pardeep is red. A run still going does not block; gh missing/offline only warns. Only the card that FIXES the red pushes with `--fixes-red`; `--owner-override` only when Pardeep says so (both are logged in the lock folder's `_ci-gate.log` — also write it in the card's liveLog). When the push changes `supabase/migrations/*.sql`, push first runs the SQL tests that mention a function/table/view those migrations create, on the LOCAL DB (migration + test in one rolled-back transaction); one red → no push (exit 5). Local DB down → warn and skip. Run it alone: `worker-lock sql-related <CARD>`. **R-1955 (26 Oct):** a red test is compared with the same test WITHOUT the card's migrations; red both ways = old local breakage → warn only — but that is a proof only when none of the card's migrations is already on the local DB (its `-- deploy-peek:` true). An applied migration cannot be taken out inside the transaction, so a red then is "not proven" (`? <test>: laal — PROOF NAHI BANA`): exit 5, logged in `_ci-gate.log` (`related-sql-not-proven`). Way on: get a local DB without the card's migration (`npx supabase db reset` from a worktree on `anutech/manager-pardeep` — wipes local data, ask Pardeep first) and run `sql-related` again; or, with Pardeep's OK, push with `--skip-related-sql` (logged; write it in the liveLog). Logic: `production/scripts/ops/worker-lock-sql.mjs`.

**Never undo another card's work (R-1958, 26 Oct 2026) — exit 9.** `worker-lock check` (on the working tree) and `worker-lock push` (before the rebase and again after it) read the diff from the merge-base with `anutech/manager-pardeep` and refuse with **exit 9** and the list of files when: (1) an existing file OUTSIDE the card's claim (the `claim` paths + the card file's `files`) is changed or deleted — generated files (deploy-db scripts, peeks.generated.ts, database.generated.ts, docs/API.md), tests named after claimed code and any new test are fine; a new non-test file outside the claim only warns; (2) an existing `supabase/migrations/*.sql` or `prisma/migrations/**` file is changed, deleted or renamed (new migrations are fine); (3) a file goes back to the exact version from before another card's commit of the last 7 days, or the diff deletes at least half (and 3+) of the lines another card added in the last 7 days. The usual cause is `git reset --soft` onto a base that moved: never fix it by force — re-apply ONLY your own files on a fresh `anutech/manager-pardeep` and run `check` again. If the card genuinely must change that file: add it to the claim, or pass `--allow-outside <path>` (repeatable; logged in the lock folder's `_scope-guard.log` — also write it in the card's liveLog). No lock/claim found → rule 1 only warns; a range with merge commits → rules 1 and 3 only warn; git itself failing → warn, never block.

## Picking up a stopped card — any member, any machine (R-1898)

Pardeep (25 Oct): any team member's Claude Code must be able to carry on any other member's stopped card, both ways.

- **The board card is the truth.** A stopped card is `doing` with a quiet liveLog (or freed back to `list` by the 60-min auto-free) whose last line says "done … next …" and whose `branch` field names `wip/<card>`.
- **Half-done work lives on GitHub,** never only on one laptop: `worker-lock.mjs wip <CARD>` pushes the worktree HEAD to `anutech wip/<card lowercase>` (force-with-lease, only on that one branch; it refuses any other name).
- **To resume** (from the production/ folder of a clone or worktree that is on the latest `anutech/manager-pardeep` — not a main clone sitting on an older branch, whose worker-lock may not have `resume`; see "Run worker-lock from a worktree" above):
  1. Read the card (ArtifactData get, out_dir). Its last liveLog line says where it stopped.
  2. `node scripts/ops/worker-lock.mjs resume <CARD> <home>/reselleros-w-<card lowercase>` — fetches `anutech/wip/<card>` and creates the worktree on branch `w-<card lowercase>` from it (no `wip/<card>` on GitHub → nothing to resume; start from `anutech/manager-pardeep`).
  3. Re-claim the card in YOUR person's name: `status: doing`, `claimedBy` = your person, `claimedAt` (`date -u`), liveLog "picked up from <person> — <where it stood>; next …". Then the junction/.env.local/prisma steps and `claim` from step 1–2 above.
  4. Carry on from the "next" in the last liveLog. Keep using `wip <CARD>` at each green step.
- **The final push** to `manager-pardeep` is still ONLY `worker-lock.mjs push <CARD>` — a wip branch is never merged by hand.
- Never `wip`-push, resume over, or merge onto a card someone else has in `doing` with a fresh liveLog — ask them (or Pardeep) first.
