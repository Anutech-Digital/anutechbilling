## 🔵 Found and fixed 14 Aug while chasing a "deploy is broken" report

The deployed `/leads` showed **"Something went wrong"**. Two separate causes, neither
of them the deploy:

1. **Browser cache poisoning (not an app bug at all).** Supabase REST sends no
   `Cache-Control` and no `Vary: Origin`, and echoes the request Origin into
   `Access-Control-Allow-Origin`. So the cache key is just the URL, and a response
   cached while on `http://localhost:3000` gets replayed to the Cloud Run origin still
   carrying `Access-Control-Allow-Origin: http://localhost:3000` — every client-side
   query fails CORS. Proven live: `fetch(url,{cache:'default'})` blocked,
   `{cache:'reload'}` fine. Fixed by pinning `cache: "no-store"` on the browser
   Supabase client (`49b809e`), the twin of the rule the admin client already followed.
   **Only hits a machine that visits both origins** — a customer never can. It costs
   debugging sessions, not customers.
   *If it recurs before the deploy lands: Ctrl+Shift+R.*

2. **An unbounded render loop of ours, which is why the page DIED instead of degrading.**
   `useDraftGuard` calls `setDraft` from an effect that depends on `setDraft`; the
   reducer always returned a new `tabs` array even for a no-op write; the provider
   rebuilt every callback whenever `tabs` changed identity. New array → new `setDraft`
   → effect fires → new array. No exit. React threw #185 at 50 nested updates, and that
   secondary error escaped the `(app)` error boundary **while it was mounting**, so the
   operator lost the whole shell and got bare `global-error.tsx`. Fixed in `a12de41`
   (reducer bails out on no-op · api callbacks are stable · `isNavigating` dep restored),
   with 6 reference-identity tests. Reproduced and verified before/after in the browser.

   ⚠️ **Worth internalising:** the app error boundary is designed to keep the operator
   inside the app with a way out (§24). It never got the chance. Any error thrown while
   `error.tsx` mounts skips it entirely and lands on the bare full-page fallback — so a
   "Something went wrong" with **no sidebar** means *two* things broke, not one.

## 🐞 Found in production data — FIXED 14 Aug (and the diagnosis above it was wrong)

- [x] **email_log mislabelled the provider on a failed Gmail send.**

      ⚠️ **The original entry here blamed the wrong line and told the wrong story.**
      It said `send.ts:135` (the `decision.blocked` path) hardcoded `provider: "resend"`,
      and that "the resolver fell back to Resend and the log recorded the fallback".
      Both wrong, and worth keeping visible because the wrong story was the plausible one.

      **What actually happened.** Line 135 could never have produced that row: it logs
      `decision.blocked` verbatim, and every possible blocked string is composed in
      `provider.ts` and ends in *"…cannot be sent at all"* / *"No email provider is
      configured…"*. None can start with `Gmail reauth_required`. Only one line in the
      codebase emits that shape — the Gmail-failure return, `` `Gmail ${r.failure}: ${r.detail}` ``
      — and **that return omitted `provider` entirely**, so the `?? "resend"` default at the
      `recordEmail` call filled in a confident wrong answer.

      **So there was no fallback.** Gmail was chosen, Gmail was attempted, Gmail failed, and
      `sendEmailInner` returned right there. Resend never saw the message. The row was not
      mislabelling a fallback — it was mislabelling a send that never happened, which also
      means **that email did not go out at all**.

      **Fixed:**
      - Gmail-failure return now says `provider: "gmail"`.
      - `EmailSendResult.provider` is now **required**, and the `?? "resend"` default is gone.
        A return statement that forgets it no longer compiles. This is the actual fix — the
        one-line version would have left the next return point free to make the same mistake.
      - The blocked path now records **the provider the tenant CHOSE** (new
        `ProviderDecision.requested`), not the resolver's fallback. That was the design call
        the old entry asked for: when nothing sent, "which one carried it" has no answer, and
        the tenant's choice is both the only true thing left and the thing an operator
        searches by.
      - Resend + stub paths now state their provider explicitly instead of relying on the default.

      `src/lib/email/send.test.ts` — 7 tests, including the exact production row inverted.

- [ ] **Still open, needs a migration: a SILENT fallback is invisible in SQL.**
      When a tenant is on Gmail, Gmail is unusable, and Resend *is* configured, the message
      really does go out via Resend — so `provider=resend, status=sent` is truthful. But it
      means a tenant whose Gmail broke weeks ago looks perfectly healthy in `email_log`, and
      the only trace is a `console.warn` nobody reads. `where provider='gmail'` finds nothing
      because nothing was sent as Gmail. Wants a `requested_provider` (or `fell_back`) column
      on `email_log`; `decision.requested` already carries the value, so it is a migration
      plus one field, not a redesign.
